# ПР01. Граф ROS 2 и разрыв связи между доменами

Среда выполнения — WSL2, Ubuntu 24.04.5 LTS, ROS 2 Jazzy.
Для эксперимента использовались `ROS_DOMAIN_ID=16` и `ROS_DOMAIN_ID=17`.

[Версии среды](environment.json) · [ROS Doctor](doctor.txt)

## 1. Исправная система

Терминал A: `ROS_DOMAIN_ID=16`, запущен `ros2 run turtlesim turtlesim_node`.

Терминал B: `ROS_DOMAIN_ID=16`, запущен
`ros2 run turtlesim turtle_teleop_key`.

Терминал C: `ROS_DOMAIN_ID=16`, выполняются команды наблюдения.

Командой

```bash
ros2 node list --no-daemon --spin-time 2
```

проверено наличие `/teleop_turtle` и `/turtlesim`.

Полный вывод: [nodes-before.txt](nodes-before.txt).

| Нода | Роль |
|---|---|
| `/teleop_turtle` | Получает ввод с клавиатуры и публикует команды движения |
| `/turtlesim` | Принимает команды движения и публикует состояние черепахи |

Интерфейсы нод дополнительно проверены командами `ros2 node info`:
[/turtlesim](turtlesim-info.txt) и
[/teleop_turtle](teleop-info.txt).

### Топики и типы

Список топиков и их типов сохранён в
[topics.txt](topics.txt).

Основной поток управления:

```text
клавиша ↑
    │
    ▼
/teleop_turtle
    │
    │ /turtle1/cmd_vel
    ▼
/turtlesim
    │
    │ /turtle1/pose [turtlesim/msg/Pose]
    ▼
CLI-подписчики ros2 topic echo / ros2 topic hz
```

Команда

```bash
ros2 topic type /turtle1/pose
```

вернула:

```text
turtlesim/msg/Pose
```

Результат сохранён в [pose-type.txt](pose-type.txt).

### Получение позы и движение

До нажатия клавиши ↑ была получена поза:

```yaml
x: 5.544444561004639
y: 5.544444561004639
theta: 0.0
linear_velocity: 0.0
angular_velocity: 0.0
```

После нажатия ↑ и остановки черепахи координата `x` стала:

```text
7.4964447021484375
```

Координата `y` осталась:

```text
5.544444561004639
```

Таким образом, изменение координаты `x` подтверждает получение команды
управления симулятором.

Первичные данные:
[до нажатия](pose-before.txt) ·
[после нажатия](pose-after-key-working.txt).

## 2. Частота `/turtle1/pose`

Частота публикации позы измерялась командой:

```bash
timeout --signal=INT 15s ros2 topic hz /turtle1/pose
```

Фактическая длительность выполнения составила:

```text
15.240 s
```

Полученная частота публикации составляла примерно:

```text
62.49 Hz
```

Полные результаты:
[частота](pose-hz.txt) ·
[длительность](pose-hz-duration.txt) ·
[код завершения](pose-hz-exit.txt).

Завершение по таймауту в данном измерении ограничивает продолжительность
работы `ros2 topic hz` и не означает отсутствие сообщений: статистика частоты
была успешно получена.

## 3. Разрыв связи между доменами

`turtlesim_node` в терминале A был оставлен в `ROS_DOMAIN_ID=16`.

`turtle_teleop_key` в терминале B был остановлен, после чего терминал B
переведён в другой домен:

```bash
export ROS_DOMAIN_ID=17
ros2 run turtlesim turtle_teleop_key
```

Терминал C также был переведён в `ROS_DOMAIN_ID=17`.

В этом состоянии список обнаруженных нод сохранён в
[nodes-broken.txt](nodes-broken.txt).

Попытка получить `/turtle1/pose` из домена 17 была ограничена таймаутом
5 секунд. Сообщение с позой не было получено, а команда завершилась с:

```text
exit=124
```

Результаты:
[pose-broken.txt](pose-broken.txt) ·
[pose-broken-exit.txt](pose-broken-exit.txt).

После этого в `turtle_teleop_key`, находящемся в домене 17, была нажата
клавиша ↑.

Для независимой проверки состояния симулятора поза была прочитана из его
рабочего домена 16. Координата осталась:

```text
x: 7.4964447021484375
y: 5.544444561004639
theta: 0.0
```

То есть нажатие ↑ из домена 17 не изменило положение черепахи,
работающей в домене 16.

Контрольная запись:
[pose-after-key-broken-control.txt](pose-after-key-broken-control.txt).

## 4. Восстановление связи

`turtle_teleop_key` был остановлен и повторно запущен с:

```bash
export ROS_DOMAIN_ID=16
ros2 run turtlesim turtle_teleop_key
```

Терминал C также был возвращён в `ROS_DOMAIN_ID=16`.

После восстановления домена снова были обнаружены необходимые ноды:
[nodes-fixed.txt](nodes-fixed.txt).

Получение `/turtle1/pose` снова стало успешным:

```text
exit=0
```

Данные:
[pose-fixed.txt](pose-fixed.txt) ·
[pose-fixed-exit.txt](pose-fixed-exit.txt).

Перед новым нажатием ↑ координата составляла:

```text
x: 7.4964447021484375
```

После нажатия ↑:

```text
x: 9.512444496154785
```

Результат сохранён в
[pose-after-key-fixed.txt](pose-after-key-fixed.txt).

Таким образом, после возврата teleop в тот же ROS-домен управление
восстановилось.

| Проверка | Исправно | Разрыв | Восстановлено |
|---|---|---|---|
| Домен A / B / C | 16 / 16 / 16 | 16 / 17 / 17 | 16 / 16 / 16 |
| Получение позы в C | Работает | Таймаут, `exit=124` | Работает, `exit=0` |
| x после ↑ | 7.496445 | 7.496445 — не изменилась | 9.512444 |
| Управление | Работает | Не работает | Работает |

### Причина

`ROS_DOMAIN_ID` разделяет участников ROS 2 на области обнаружения.
В проведённом эксперименте `turtle_teleop_key` в домене 17 не взаимодействовал
с `turtlesim_node`, оставшимся в домене 16. Аналогично CLI-подписчик,
запущенный в домене 17, не получил сообщения `/turtle1/pose` от симулятора
из домена 16.

Изменение `ROS_DOMAIN_ID` через `export` изменяет окружение для последующих
процессов, но не изменяет домен уже работающей ноды. Поэтому после смены
домена `turtle_teleop_key` запускался заново.

После возврата `turtle_teleop_key` и терминала наблюдения в домен 16
обнаружение и передача сообщений восстановились.

## 5. Итог

Эксперимент воспроизвёл нарушение связи между ROS 2 нодами при использовании
разных `ROS_DOMAIN_ID`.

В исправном состоянии нажатие ↑ изменило `x` с `5.544444561004639`
до `7.4964447021484375`.

После переноса teleop в домен 17 нажатие ↑ не изменило `x`, а попытка
получить позу в домене 17 завершилась с `exit=124`.

После возврата в домен 16 получение позы завершилось с `exit=0`,
а новое нажатие ↑ изменило `x` с `7.4964447021484375`
до `9.512444496154785`.

Следовательно, наблюдаемая неисправность была вызвана разделением
участников по разным ROS-доменам, а возврат в общий домен восстановил связь.
